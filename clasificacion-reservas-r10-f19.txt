1. REQUERIMIENTOS CUBIERTOS
────────────────────────────────────────────────────────────────────────────────

F4.1 (Rol Cliente Particular). Crear reserva:
  - El sistema clasifica los bienes de la reserva en base a su descripción textual.
  - Si no puede determinar la categoría, notifica al Operador en menos de 1 segundo.

F19 (Rol Operador). Clasificación de reservas no reconocidas:
  - El Operador recibe notificaciones en tiempo real de reservas sin categoría.
  - Puede asignar la categoría MOVE manualmente.
  - Si el bien está fuera del catálogo MOVE, puede enviar correo al cliente.

R10. Evaluación comparativa de 3 tecnologías para clasificación:
  - IA Generativa local (Ollama)
  - Búsqueda semántica (TF-IDF cosine similarity)
  - Coincidencia por palabras clave (Keyword/Bag-of-Words)

2. PATRONES Y TÁCTICAS ARQUITECTÓNICAS APLICADAS
────────────────────────────────────────────────────────────────────────────────

2.1 Pub/Sub (Publisher–Subscriber) — patrón central
  Hay dos eventos en el bus y dos suscriptores independientes:

  PUBLICADORES:
    - ControladorClientePersonal publica 'reserva:creada' al crear una reserva.
    - El Suscriptor 1 publica 'reserva:no-reconocida' si la clasificación falla.

  SUSCRIPTORES:
    - Suscriptor 1: escucha 'reserva:creada' → corre la clasificación.
    - Suscriptor 2: escucha 'reserva:no-reconocida' → notifica operadores por SSE.

  Beneficio: cada componente solo conoce el bus, no a los otros.
  El controlador no sabe nada de clasificación. El SSE no sabe nada de clasificación.
  Cada suscriptor tiene una única responsabilidad.

2.2 Server-Sent Events (SSE) para push en tiempo real
  - El operador se suscribe a GET /api/notificaciones/stream.
  - El servidor mantiene la conexión abierta (text/event-stream).
  - Cada evento publicado en el bus interno se traduce a un mensaje SSE.
  - El browser reconecta automáticamente ante desconexiones (comportamiento estándar SSE).
  - Más simple que WebSocket para comunicación unidireccional servidor → cliente.

2.4 Timeout + Degradación gradual para la IA generativa (Ollama)
  - Si Ollama no responde en 800ms, se aborta la petición (AbortController).
  - El sistema continúa funcionando con los métodos rápidos (keyword + TF-IDF).
  - Ollama corre en background independientemente y actualiza la reserva si tiene éxito.

2.5 Estrategia de clasificación en capas
  - Capa 1 (instantánea, ~1ms): Keyword matching
  - Capa 2 (rápida, ~20-50ms): TF-IDF cosine similarity
  - Capa 3 (lenta, variable): IA Generativa local (Ollama)
  - Las capas 1 y 2 determinan si se debe notificar al operador (<100ms, < 1 segundo).
  - La capa 3 sigue corriendo en background y puede actualizar la reserva post-facto.

3. FLUJO PASO A PASO: CLIENTE PARTICULAR CREA UNA RESERVA
────────────────────────────────────────────────────────────────────────────────

Paso 1 — El cliente POST /api/clientes-personales/realizar-reserva
  Body: { origen, destino, fecha, costo, productos: [id1, id2, ...] }
  No envía categorías — las infiere el sistema.

Paso 2 — ControladorClientePersonal.realizarReserva()
  Llama a servicioReserva.crearReserva() con categorias = [].
  La reserva se guarda en la DB sin categorías.

Paso 3 — Respuesta inmediata al cliente (HTTP 201)
  El cliente recibe la confirmación de la reserva sin esperar clasificación.

Paso 4 — setImmediate() lanza la clasificación asíncrona
  (Corre en el siguiente ciclo del event loop, no bloquea nada.)

Paso 5 — Se obtienen las descripciones de los productos de la reserva
  SELECT descripcion FROM producto WHERE id = ANY([ids de la reserva])

Paso 6 — clasificarRapido(descripcionCombinada) corre Keyword + TF-IDF en paralelo
  Promise.all([clasificarConKeyword(), clasificarConTFIDF()])
  Tiempo estimado: < 100ms

Paso 7a — Si algún método encontró categoría:
  UPDATE reserva SET categorias = ['categoría encontrada'] WHERE id = ?
  Fin del flujo — reserva queda categorizada.

Paso 7b — Si ningún método rápido encontró categoría:
  busEventos.emit('reserva:no-reconocida', { reservaId, clienteId, descripciones, resultados, timestamp })
  Tiempo desde la creación de la reserva: < 200ms (muy por debajo de 1 segundo).

Paso 8 — El bus interno notifica a todos los suscriptores del evento
  El listener en index.ts itera sobre todos los clientes SSE conectados (operadores)
  y escribe: data: { tipo: 'reserva-no-reconocida', ... }\n\n

Paso 9 — El browser del Operador recibe el evento SSE
  La función onmessage() agrega la reserva al panel de F19.
  Se muestra badge "NUEVO" con el contador actualizado.

Paso 10 — En background, Ollama sigue intentando clasificar
  Si tiene éxito, UPDATE reserva SET categorias = ... (sin nuevo evento al operador).

────────────────────────────────────────────────────────────────────────────────
4. FLUJO PASO A PASO: OPERADOR CLASIFICA RESERVA NO RECONOCIDA (F19)
────────────────────────────────────────────────────────────────────────────────

Paso 1 — Operador entra a /reservas-no-reconocidas-ui
  La página se conecta a GET /api/notificaciones/stream (SSE).

Paso 2 — Operador ve las reservas pendientes con los resultados de cada método
  Se muestran los 3 badges con: método, categoría sugerida (o "sin resultado"), tiempo en ms.

Paso 3a — Operador selecciona una categoría del listado MOVE y hace click "Asignar"
  PATCH /api/reservas/{id}/categorias  body: { categorias: ['categoría'] }
  UPDATE reserva SET categorias = ? WHERE id = ?

Paso 3b — Si el bien está completamente fuera del catálogo MOVE:
  Operador hace click "Enviar correo (bien fuera de catálogo)"
  POST /api/reservas/{id}/notificar-sin-categoria  body: { clienteId }
  El sistema registra en log (en producción enviaría email real vía servicio externo).

6. LOS 3 MÉTODOS — DESCRIPCIÓN TÉCNICA
────────────────────────────────────────────────────────────────────────────────

6.1 KEYWORD MATCHING (Bag-of-Words)
  Archivo: ServicioGestion/src/ModuloCatalogo/Servicio/ServicioClasificacion.ts

  Cómo funciona:
    - Tokeniza la descripción y los textos de cada categoría (nombre + nombre_es + descripción).
    - Normaliza: minúsculas, quita tildes, quita puntuación, filtra palabras < 3 letras.
    - Cuenta cuántas palabras de la descripción aparecen en el texto de cada categoría.
    - Selecciona la categoría con más coincidencias.
    - Confianza = palabras_coincidentes / total_palabras_descripción (umbral: 5%).

  Ventajas: Extremadamente rápido (~1ms), sin dependencias, 100% offline.
  Desventajas: No entiende sinónimos ni contexto semántico.

  Complejidad: O(n * m) donde n = categorías, m = tokens de la descripción.

6.2 TF-IDF COSINE SIMILARITY (Búsqueda Semántica Clásica)
  Archivo: ServicioGestion/src/ModuloCatalogo/Servicio/ServicioClasificacion.ts

  Cómo funciona:
    - TF (Term Frequency): frecuencia de cada palabra en un documento.
    - IDF (Inverse Document Frequency): log(N / df) — penaliza palabras comunes.
    - Cada categoría se representa como un vector TF-IDF en un espacio de alta dimensión.
    - La descripción también se vectoriza.
    - Se calcula la similitud coseno entre la descripción y cada categoría.
    - La categoría con mayor coseno (umbral: 0.1) es la ganadora.

  Ventajas: Mejor que keyword, considera importancia relativa de las palabras.
    Implementado en TypeScript puro, sin dependencias externas.
  Desventajas: No entiende semántica profunda (sinónimos, paráfrasis).

  Complejidad: O(n * m) por build + O(n * k) por scoring, donde k = términos únicos.

6.3 IA GENERATIVA LOCAL (Ollama)
  Archivo: ServicioGestion/src/ModuloCatalogo/Servicio/ServicioClasificacion.ts

  Cómo funciona:
    - Llama al endpoint POST http://localhost:11434/api/generate con modelo llama3.2.
    - El prompt lista las primeras 50 categorías MOVE y pide identificar la más apropiada.
    - Parsea la respuesta buscando coincidencias con los nombres de categorías.
    - AbortController cancela la petición si supera 800ms (timeout configurable por .env).
    - En caso de timeout, devuelve error gracioso y el sistema continúa con los otros métodos.

  Ventajas: Mayor precisión, comprende contexto y sinónimos.
  Desventajas: Lento (segundos), requiere Ollama instalado y corriendo en localhost:11434.

  Variables de entorno:
    OLLAMA_URL=http://localhost:11434  (por defecto)
    OLLAMA_MODEL=llama3.2             (por defecto)

8. CRITERIO ELEGIDO PARA MÚLTIPLES BIENES EN UNA RESERVA
────────────────────────────────────────────────────────────────────────────────

Cuando una reserva tiene más de un bien (ej: "un monitor y una silla"), el sistema
combina todas las descripciones en un solo texto y clasifica una sola vez.
Se toma la categoría con mayor puntuación del método utilizado.

Criterio: "primera categoría inferida del texto combinado".
Justificación: el profe confirmó en el foro que cualquier criterio es válido y que
ninguno tiene impacto significativo a nivel arquitectónico.

9. CÓMO PROBAR
────────────────────────────────────────────────────────────────────────────────

Paso 1 — Levantar Docker (postgres + Ollama)
  Desde ServicioGestion/:
    docker-compose up -d
  La primera vez, el contenedor ollama-setup descarga el modelo tinyllama (~637MB).
  Esperar hasta ver en los logs: "Modelo tinyllama descargado."

Paso 2 — Reiniciar ServicioGestion
  npm run dev  (o ts-node src/index.ts)
  Ollama queda accesible en http://localhost:11434

Paso 3 — Abrir /reservas-no-reconocidas-ui como Operador.
  La página queda escuchando eventos SSE (conexión abierta al servidor).

Paso 4 — En otra pestaña, como ClienteParticular, crear una reserva con productos
  cuya descripción no coincida con ninguna categoría (ej: "objetos varios raros").

Paso 5 — En la pestaña del Operador aparece la notificación automáticamente con:
  - ID de reserva, cliente, descripciones de bienes
  - Badge de cada método: categoría sugerida (o "sin resultado") + tiempo en ms

Paso 6 — El Operador asigna la categoría correcta manualmente.

Paso 7 — Para probar el comparador R10:
  Ingresar una descripción en "Comparador de métodos" → "Comparar los 3 métodos".
  Los 3 resultados aparecen lado a lado con tiempos de respuesta reales.

Variables de entorno opcionales (.env):
  OLLAMA_URL=http://localhost:11434   (por defecto)
  OLLAMA_MODEL=tinyllama              (por defecto)
